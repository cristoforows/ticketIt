# Barebones CI for existing checks

## Purpose

Adds GitHub Actions CI that runs, automatically on every pull request
and on push to `main`, the checks that already existed but that
nothing ran unless a human remembered to: Galley's build/test suite
against real PostgreSQL, Swiftlet's test/build, and both contract-drift
scripts (`apps/galley/scripts/check-contract-drift.sh`,
`contracts/check-swiftlet-drift.sh`). Touches only `.github/**`
plus this one evidence record. Tracking issue: [#68 — M2.15 — Barebones CI for existing
checks](https://github.com/cristoforows/ticketIt/issues/68), under
[M2 (#3)](https://github.com/cristoforows/ticketIt/issues/3). Blocked
by [#52](https://github.com/cristoforows/ticketIt/issues/52) (merged),
which is why Galley's job needs a PostgreSQL service at all.

## What already existed

No `.github/` directory of any kind. `apps/galley` (Go, `go build
./...`, `go test ./...` against real PostgreSQL, `gofmt`, `go vet`),
`apps/swiftlet` (`npm ci`, `npm test`, `npm run build`), and
`contracts/` (both drift scripts) all already existed and all already
worked when run by hand — [#51](https://github.com/cristoforows/ticketIt/issues/51)
and [#52](https://github.com/cristoforows/ticketIt/issues/52) each
recorded the same gap this issue names: none of it ran automatically.
No sibling slice was landing in parallel that this one depended on.

This issue's own comment (added while writing #62's gate report)
records that [#53](https://github.com/cristoforows/ticketIt/issues/53)
landed a browser/e2e suite (`e2e/run.sh`) after this issue's body was
written, and that wiring it into CI was deliberately left for whoever
picked this issue up next — see "Outstanding checks" below.

## What this slice added

`.github/workflows/ci.yml`: one workflow, `on: pull_request` and
`on: push` to `main`, three jobs with no `needs:` between them (jobs
run independently by default; no Swiftlet failure can mask a Galley
failure, proven directly below). `.github/workflows/README.md`
documents how to reproduce each job locally.

- **`galley`**: a `postgres:17` service container
  (`ticketit_test`/`postgres`/`postgres`, mapped to `localhost:5432`),
  Go 1.27.1, then `go run ./cmd/migrate` (`DATABASE_URL` set, per
  `apps/galley/README.md`, "Database migrations" — the suite itself
  would apply migrations anyway via `NewTestPool`, but the issue asks
  for an explicit step), `gofmt -l .` (fails and prints the offending
  files on any output), `go vet ./...`, `go build ./...`, `go test
  ./...` (`GALLEY_TEST_DATABASE_URL` set to the same service
  database).
- **`swiftlet`**: Node 26.9.0, `npm ci`, `npm test`, `npm run build` —
  the exact sequence `apps/swiftlet/README.md` documents.
- **`contracts`**: both toolchains (Go 1.27.1 and Node 26.9.0) on one
  clean checkout, then `apps/galley/scripts/check-contract-drift.sh`
  and (`npm ci` first, in `contracts/`) `contracts/check-swiftlet-drift.sh`.

Every `uses:` is pinned to a commit SHA with the tag as a trailing
comment, per the issue's own scope.

### Decisions the issue did not dictate

1. **`actions/setup-go` needed an explicit `cache: false`.** The
   first real CI run's own annotations surfaced this: `actions/setup-go`
   v5's `cache` input [defaults to `true`](https://github.com/actions/setup-go/blob/40f1582b2485089dde7abd97c1529aa768e1baff/action.yml#L16-L18)
   — silently enabling Go module caching unless disabled, which would
   have contradicted the issue's own explicit "no dependency caching"
   exclusion without a single `cache:` line anywhere admitting it. Set
   explicitly in both jobs that use `setup-go`. `actions/setup-node`
   needed no equivalent override — its `cache` input has no default
   and is opt-in only (confirmed by reading its `action.yml` directly
   rather than assuming symmetry between the two actions).
2. **A `pg_isready` health check on the postgres service container**
   (`options:`), not asked for explicitly. GitHub Actions starts a
   service container immediately, before it necessarily accepts
   connections; without this, `go run ./cmd/migrate` (the first real
   step) can race a not-yet-ready server. This is infrastructure
   plumbing for the one service container the issue does ask for, not
   scope creep.
3. **One workflow file, three jobs**, rather than three separate
   workflow files — satisfies "jobs run independently" for free (no
   `needs:` between them), with one place to read the whole CI surface.
4. **Each Galley sub-check is its own named step** (`Apply migrations`,
   `gofmt`, `go vet`, `go build`, `go test`) rather than one combined
   script, so a red run's job summary names the exact failing check
   without opening logs.
5. **Action SHAs pinned to each action's latest tag as of 2026-09-22**
   (`git ls-remote --tags`, confirmed unannotated so the tag and commit
   SHA are the same object): `actions/checkout` `v4.4.0`
   (`11d5960a326750d5838078e36cf38b85af677262`), `actions/setup-go`
   `v5.6.0` (`40f1582b2485089dde7abd97c1529aa768e1baff`),
   `actions/setup-node` `v4.4.0` (`49933ea5288caeca8642d1e84afbd3f7d6820020`).
6. **`DATABASE_URL` and `GALLEY_TEST_DATABASE_URL` both point at the
   same service-container database** (`ticketit_test`, inside the
   ephemeral container — unrelated to and never touching the shared
   local `ticketit_test` this repository's contributors use by hand).
   The explicit migrate step and the suite's own idempotent
   `NewTestPool` migration both target it; no conflict, since
   golang-migrate's own apply is a no-op the second time.
7. **Go/Node versions are literal strings** (`"1.27.1"`, `"26.9.0"`)
   matching the issue's own wording, not `go-version-file`/
   `node-version-file` pointed at `go.mod`/`package.json` — either
   would satisfy the issue; this keeps the pin visible in the one file
   that also pins every action, rather than split across two files.
8. **The postgres image itself (`postgres:17`) is a tag, not a pinned
   digest.** The issue's pin-to-SHA instruction names GitHub Actions
   specifically ("Pin every action..."); a service container image is
   a different mechanism the issue does not mention, and digest-pinning
   it is exactly the kind of extra hardening this slice's "barebones"
   framing and explicit non-goals (no matrix builds, no extra rigor
   beyond what's asked) argue against adding unasked.

## Reproducible commands

See `.github/workflows/README.md` for the exact per-job commands (they
are not repeated here to avoid a second copy drifting from the first).

**Pre-flight** (run once before writing the workflow, against a
genuinely fresh database — the local `ticketit_test` is shared,
long-lived, and already holds hundreds of rows plus one bootstrapped
Owner, which could hide a test's undisclosed dependency on accumulated
state that a fresh CI database would expose):

```sh
createdb ticketit_ci_probe
cd apps/galley
DATABASE_URL=postgres://localhost:5432/ticketit_ci_probe?sslmode=disable go run ./cmd/migrate
gofmt -l .
go vet ./...
go build ./...
GALLEY_TEST_DATABASE_URL=postgres://localhost:5432/ticketit_ci_probe?sslmode=disable go test ./... -count=1
```

## Outstanding checks and owning milestone

- **The browser/e2e suite (`e2e/run.sh`) is not wired into this
  workflow**, per the issue's own explicit scope (ticked boxes only;
  this was left unticked) and per this issue's own comment (added
  while #62's gate report was being written): #53 landed `e2e/run.sh`
  after this issue's body was written, and #54–#61 each extended it,
  but nobody has picked up wiring it into CI. That comment names three
  concrete blockers for whoever does:
  - `e2e/run.sh` calls `createdb`/`dropdb`/`psql` directly against "the
    current user's PostgreSQL" (`e2e/README.md`, "Determinism and
    state reset") — a CI service container needs these pointed at the
    container host via `E2E_DATABASE_URL`.
  - The runner image needs `postgresql-client` tools available for
    that.
  - The suite installs Chromium's headless shell on first run
    (`playwright install chromium --only-shell`, ~200MB) — worth
    caching between runs, which this issue's own "no caching" scope
    exclusion does not apply to (no e2e job exists here to cache
    anything for).
  No issue currently owns this; per #62's own instruction not to file
  a duplicate, it stays recorded on #68 (this issue) until someone
  picks it up.
- **Marking these checks required in GitHub's branch protection
  settings** is a repository setting, not a file — the issue itself
  names this as something an agent cannot and should not do. The
  Owner does this once this PR is green.
- **CI automation was itself the outstanding check every prior M2
  evidence record named** ("CI automation of the commands recorded
  here — no owning issue yet"); this slice is that follow-up landing.
